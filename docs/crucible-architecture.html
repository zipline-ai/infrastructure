01 · Product contract

Run the data plane in the customer account.

Crucible replaces an external compute backend with Kubernetes-native submission. The Hub remains the workflow control point. Spark, Flink, and Ray workloads run in compute namespaces.

User outcome

One workflow surface

The Zipline CLI and UI use the same Hub workflow APIs for batch and streaming work.

Compute outcome

Elastic EKS workloads

Operators create engine pods. Karpenter supplies role-specific nodes when matching pools exist.

Isolation outcome

Team namespaces

Namespaces provide RBAC, quotas, service accounts, and a stable routing boundary.

Compatibility outcome

Spark 4 only

The AWS Crucible chart selects Spark 4 Hub, Eval, engine, and Flink-compatible artifacts.

Required invariants

  • The Hub starts with IN_CLUSTER_COMPUTE_ENABLED=true. Backend selection is deployment-wide, not per job.
  • The default team maps to zipline-default. Other teams map to sanitized zipline-<team> names.
  • Workload custom resources and pods run in compute namespaces. Control services run outside them.
  • The Platform image version and the Chronon artifact version identify a compatible release set.
  • Iceberg table metadata is served through Polaris. Table data is stored in S3.

Non-goals

  • This document covers only the AWS Crucible deployment.
  • A single Hub does not choose between Crucible and an external AWS compute backend per submitted job.
  • Namespaces do not place pods on nodes by themselves. Selectors, taints, tolerations, and matching node pools do that.
  • The current implementation does not provide complete Ray role placement or per-mode resource quotas.
  • This document does not claim that every component is highly available.

04 · Repository ownership

Three repositories form one release path.

Each repository owns a different contract. A successful release needs compatible code and versioned artifacts across all three.

Chronon

Configuration and engines

  • CLI compilation, diff, upload, run, schedule, cancel, fetch, and eval commands.
  • Spark batch runner, Flink job, online Fetcher, and cloud integration JARs.
  • Spark 3 and Spark 4 artifacts. AWS Spark 4 names include _spark4_.

Platform

Workflow and submission

  • Hub APIs, planning, scheduling, status, logs, UI proxying, and cancellation.
  • Team-to-namespace routing and CRD construction for Spark, Flink, and Ray.
  • AWS Hub, Eval, UI, and Fetcher container images.

Infrastructure

AWS and Kubernetes topology

  • EKS, Karpenter, IAM, RDS, S3, DynamoDB, Glue, AMP, and load balancing.
  • Helm values, services, namespaces, quotas, service accounts, and RBAC.
  • Operator installation and system or compute node placement.

Default placement key

team=default + engine=spark|flink + role=driver|executor|jobmanager|taskmanager + a workload taint and toleration.

This creates deterministic role placement. It does not create a spending ceiling. ResourceQuota and AWS capacity controls remain separate.

Extension contract

To add a team, create its compute namespace and RBAC, generate its engine-role pools, and ensure every workload pod carries matching labels, selectors, and tolerations.

Add Ray head, worker, and submitter roles before claiming the same placement guarantee for training.

08 · Security and access

Identity crosses three enforcement layers.

External authentication protects HTTP routes. Kubernetes RBAC protects submission. IAM roles for service accounts protect AWS resources.

HTTP

Session or bearer token

Browser Hub traffic uses NGINX forward-auth through the UI. The UI mints a JWT from its session. CLI traffic presents a bearer token directly. Hub route guards validate JWTs and roles when auth is enabled.

Kubernetes

Namespaced submit and operate

The Hub service account receives a submitter RoleBinding in each compute namespace. Spark and Flink workloads use separate service accounts and namespaced runtime permissions. Hub watch access for workload CRDs is cluster-wide.

AWS

IRSA and secret materialization

Orchestration and compute service accounts assume AWS IAM roles. External Secrets copies required values from Secrets Manager into Kubernetes secrets. S3 public access is blocked.

Implemented controls

  • Public access blocks on S3 buckets, plus encrypted RDS, DynamoDB, and EKS node volumes.
  • Separate workload service accounts and namespaced RBAC.
  • OIDC-based CI credentials for artifact publication.
  • Private and public EKS API endpoints with control-plane audit and API logging.

Controls to add or verify

  • NetworkPolicies between system, compute, catalog, and data services.
  • Pod Security admission levels and workload security contexts.
  • Least-privilege review of broad compute IAM permissions.
  • Immutable image references, signature policy, and artifact integrity checks.

10 · Decision log and next work

The architecture works, but several contracts remain implicit.

These items are ordered by correctness and operability impact. They are recommendations, not claims about committed roadmap.

Gap

Install mode PriorityClasses

Define zipline-backfill and zipline-deploy in the Infrastructure chart. Choose explicit values and preemption policies. Platform already references these names on Spark, Flink, and Ray pods.

Gap

Complete Ray placement

Add default-team Ray head, worker, and submitter pools. Apply the same team/engine/role selector and toleration contract used by Spark and Flink.

Gap

Make terminal engine identity durable

Persist the namespace, CR kind, CR name, and relevant terminal links with the workflow step. Do not depend on a process-local archive after CR deletion.

Partial

Extend capacity isolation to each team

Generate the four Spark/Flink role pools per configured team. Add account-level and cluster-level capacity limits. Keep ResourceQuota for admission control.

Proposed

Pin the release set

Record Platform image digests, Chronon artifact version and checksums, chart version, and Spark/Flink image digests in one deployment manifest.

Proposed

Define recovery objectives

Set RPO and RTO for Hub RDS, Polaris RDS, S3 state, DynamoDB, Loki, and engine checkpoints. Test restore and regional failure procedures.

Proposed

Add workload network policy

Allow only required DNS, Kubernetes API, catalog, AWS endpoints, telemetry, and data-source traffic. Deny cross-team traffic by default.

Partial

Align version metadata

The current Spark image is based on Spark 4.1.3 while the generated SparkApplication declares sparkVersion: 4.1.0. Make these values originate from one release input.

Proposed

Prove service scale-out

Before increasing Hub replicas, define leader election or database leases for schedulers and pollers. Move Loki to object storage before treating log retention as highly available.
