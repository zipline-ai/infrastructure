    02 / The execution contract

    Open the layer you need.

    The diagrams follow logical handoffs. These details explain resource sizing, placement, durable state, and the services that support them.

    Team and mode quotasOverlapping ceilings, checked when each pod is created.
    Team → namespace→Run mode → PriorityClass→Pod requests + limits→All applicable quotas

    Each team namespace can have an aggregate zipline-compute quota plus zipline-backfill and zipline-deploy quotas. Mode quotas match the pod’s priorityClassName. They do not match an arbitrary pod label and they do not select physical nodes.

    QuotaWhich pods count?Example CPU request ceiling
    zipline-computeAll quota-counted pods in the namespace200 CPU across all modes together
    zipline-backfillpriorityClassName: zipline-backfill200 CPU within the shared total
    zipline-deploypriorityClassName: zipline-deploy200 CPU within the shared total

    Example: if backfill requests 150 CPU and nothing else is running, deploy can request at most another 50 CPU under a 200-CPU namespace ceiling. The mode ceilings do not add together or reserve a share for either mode.

    An empty mode hard: {} inherits the configured aggregate hard values when Helm renders the chart. Defaults are requests of 200 CPU / 800 GiB, limits of 400 CPU / 1,600 GiB, and 500 pods. Explicit per-mode hard maps can make an individual mode stricter. Quota limits describe the sum of pod resource limits; they are separate from resource-request ceilings.

    Pod labels retain team, engine, and role attribution. Flink keeps jobmanager and taskmanager role labels even though those roles share a pool. Spark and Flink tolerate zipline.ai/workload=<engine>:NoSchedule. Neither the team nor run mode is part of their node selector.

    The system pool hosts control services separately. AWS capacity constraints, architecture, instance selection, and pool ceilings are defined by aws/zipline-orchestration/node-pools.tf and its aws.karpenter overrides. Adding a team namespace does not require another set of pools.

    Pool limits cap provisioned node resources. Namespace quotas cap admitted workload resources. They are independent controls; a permitted pod can remain Pending while suitable capacity is unavailable.

    How a conf becomes pod resource requestsPer-node execution settings drive engine-specific pod sizing.

    Chronon merges default-team, team, and conf settings into metadata.executionInfo. Mode-specific settings inherit common configuration. Hub selects the resolved mode settings for each runnable node.

    Spark

    Resource properties pass through SparkApplication.spec.sparkConf. Spark translates cores, request-cores, executor count, memory, and overhead settings into driver and executor pods. Executor heap memory alone is not the complete pod memory request.

    Flink

    Hub emits separate jobManager.resource and taskManager.resource fields. JM memory comes from its process-size setting and CPU from Hub configuration. TM memory comes from its resolved resource/tier settings, while task slots influence CPU.

    Quota admission counts the resulting pod requests, limits, and pod count. It does not reserve an entire workflow’s predicted peak resources when the request reaches Hub.

    Run mode, priority, and warm capacityBackfill and deploy classify work. Pause pods keep Spark driver capacity ready.

    backfill selects backfill mode. run-adhoc selects deploy mode, which can include both Spark preparation and Flink streaming nodes. Crucible submission accepts only these two modes, using the shared Thrift enum. Its direct submission boundary rejects missing or unsupported modes.

    Internal workflow submission already supplies the mode; its engine adapters also have internal fallback defaults. Workflow API validation and terminal-node lookup are separate from Crucible’s submission validation.

    PriorityClassPriorityPurpose
    zipline-deploy200Deploy workflow pods
    zipline-backfill100Backfill workflow pods
    zipline-spark-pause−1Warm driver placeholders

    The warm deployment runs two low-priority pause pods, each requesting 2 CPU / 4 GiB, on spark-driver. Higher-priority workloads can displace those placeholders. It uses the existing pool; it is not a separate NodePool. Executor image pre-pull is a separate DaemonSet that targets executor nodes.

    Backfill and deploy use PreemptLowerPriority. This does not reserve capacity per team or allow a request to exceed its namespace quota. Mode classification uses PriorityClass; the current submitter does not automatically add a zipline.ai/mode pod label.

    Namespaces and durable stateControl state, live engine state, table data, and diagnostic history have different owners.

    zipline-system hosts Hub, UI, Eval, Polaris, optional Fetcher and Data Explorer, logs/history services, and the Spark, Flink, and KubeRay operators. External Secrets, cert-manager, and the OpenTelemetry operator also use this install namespace. kube-system contains infrastructure controllers such as Karpenter and the AWS load balancer controller. Team namespaces host workload custom resources and pods.

    Identity and accessHTTP authentication, Kubernetes RBAC, and AWS IAM apply at different boundaries.

    HTTP

    NLB and NGINX route public service traffic. When Hub authentication is enabled, browser forward-auth converts the UI session into bearer authorization; CLI tokens pass through. Hub validates JWTs and enforces viewer/operator roles. Eval has its own authentication middleware.

    Kubernetes

    Hub receives submitter permissions in configured compute namespaces and cluster-wide read/watch access to engine CRs. Spark and Flink use separate workload service accounts and namespaced permissions. Namespace and RBAC boundaries alone do not imply network isolation.

    AWS

    Service accounts assume IAM roles through IRSA. External Secrets materializes values from Secrets Manager into Kubernetes Secrets for services. Catalog access can vend scoped S3 credentials for table operations.

    Fetcher serves its own endpoints. The diagram does not imply that Hub authenticates or proxies online fetch traffic; exposure and access depend on the configured gateway.

    Monitoring, logs, and failure signalsRead each signal at the layer that owns the decision.

    The AMP scraper collects annotated workload/service metrics, both Fetcher metric ports, kube-state-metrics, Karpenter, and cAdvisor. The UI server queries AMP using signed AWS requests. Hub health and workflow state are fetched separately.

    Promtail sends pod logs to Loki. Hub reads live Kubernetes logs and retained logs. Spark History Server replays S3 event logs after an application finishes. Fluent Bit provides a separate CloudWatch log path where deployed.

    Pod exists but is PendingScheduling events, selectors, pool limits, and Karpenter provisioning
    Engine running but workflow stalledHub worker health, dependencies, and step tracking

    Installation inputs and release artifactsConfiguration is applied through Terraform and Helm; it is not hot-loaded from S3.
    S3 install inputs→pull_crucible_config.sh→Local tfvars→Terraform→Helm / AWS

    The S3 configuration supplies orchestration and aws inputs. The AWS node-pool definition stays in the infrastructure repository; tfvars override its defaults. Helm receives the resolved service settings, namespace quotas, identity, artifacts, and placement configuration.

    Chronon publishes engine artifacts; Platform publishes service images. The selected image references and Chronon artifact version form the runtime release set. Spark 4 artifact names distinguish that dependency profile. A mutable image tag alone does not identify the running source revision.

    Changing S3 inputs takes effect after a fresh pull and Terraform apply. Changing a live object directly does not update the saved inputs. The diagrams show source-defined architecture rather than temporary cluster overrides.

    03 / Repository ownership

    Three repositories. One execution path.

    chronon

    Configuration compilation, planners, CLI commands, Spark and Flink computation, model inputs, online materialization, and feature fetching.

    platform

    Hub APIs, workflow planning and scheduling, Crucible submission, engine resource specifications, UI, Eval, and monitoring queries.

    infrastructure

    AWS resources, Kubernetes installation, Helm configuration, namespaces, quotas, identity, shared capacity, and telemetry collection.
